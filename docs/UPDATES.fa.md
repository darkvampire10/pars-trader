# انتشار و به‌روزرسانی

## GitHub

نام پیشنهادی مخزن: `pars-trader`. مجوز MIT داخل پروژه است.
برای متن‌باز عمومی، مخزن Public بسازید؛ فقط کد منتشر می‌شود، نه داده‌ها و کلیدهای سرور.
اگر مخزن خالی دارید، از پوشه پروژه پس از بررسی فایل‌ها:

```bash
git init -b main
git add .
git commit -m "Initial research release"
git remote add origin <YOUR_GITHUB_REPOSITORY_URL>
git push -u origin main
```

اگر پروژه از قبل Git دارد، مراحل init/commit را تکرار نکنید؛ فقط remote معتبر را تنظیم و push کنید.
رمز/توکن GitHub را در URL مخزن یا متن دستور قرار ندهید. از SSH یا ورود امن ابزار GitHub استفاده کنید.

## هر به‌روزرسانی

1. شاخه جدید بسازید؛ کد و مستندات را با هم اصلاح کنید.
2. Pull Request بسازید. تست‌های GitHub Actions باید موفق شوند.
3. بعد از بررسی، merge کنید و tag نسخه مثل `v0.1.1` بسازید.
4. روی VPS نسخه مشخص را نصب کنید:

```bash
bash scripts/update.sh v0.1.1
docker compose ps
docker compose logs --tail=50 bot
```

این tag صرفاً نمونه است و تا انتشار واقعی وجود ندارد.
اسکریپت ابتدا نسخه مقصد را در worktree جدا تست و build می‌کند؛ سپس سرویس را متوقف و از داده‌ها backup می‌گیرد، و نسخه مشخص را اجرا می‌کند.
اگر فرمان شروع شکست بخورد، کد قبلی را برمی‌گرداند. شکست دیرهنگام healthcheck نیازمند بررسی و بازگشت دستی است.
`.env` تغییر نمی‌کند. backup شامل داده خصوصی است؛ خارج از Git و با دسترسی محدود نگهداری شود.

## بازگشت

شناسه commit قبلی در `backups/previous-*.txt` است:

```bash
docker compose stop
git switch --detach <PREVIOUS_COMMIT>
docker compose up -d --build
```

اگر نسخه جدید ساختار دیتابیس را عوض کرده، بازگشت کد کافی نیست؛ طبق راهنمای migration همان نسخه از backup داده بازیابی کنید.
نسخه ۰.۱ migration مخرب ندارد. زمان به‌روزرسانی نسخه‌های دارای معامله واقعی در آینده، باید مدیریت معاملات باز جداگانه طراحی شود.

## کمک در آینده

لینک مخزن، نسخه فعلی و خطای بدون اطلاعات محرمانه را به دستیار بدهید. دسترسی مخزن در همان جلسه لازم است.
هیچ دستیار یا GitHub Actions به‌طور پیش‌فرض پروژه را دائماً رصد یا خودکار اصلاح نمی‌کند.
